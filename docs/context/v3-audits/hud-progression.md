# v3 audit — HUD / GUI + game progression & modes
**VERDICT: REFACTOR**
## Justification
Split verdict, weighted to the end result. The pieces that are GOOD are genuinely good and rewriting them would be waste: theme.js is a correct, complete token system (theme.js:19-77) and needs only two more accent tokens; speedDisplay.js is already the best-looking element in the game and already reads theme's palette (speedDisplay.js:99-100, :126, :136, :161); minimap.js's custom canvas renderer + the citymap.bin pipeline replaced Leaflet for measured reasons and re-deriving it would burn a week to arrive back where we are — it needs a repalette, not a rebuild; wallet.js is 30 lines of correct persistence and should be extended, not replaced. Rewriting any of those would be a rebuild justified by code aesthetics, which the brief explicitly names as waste.

The pieces that are BAD are bad structurally, not cosmetically, and those get REBUILT — but the rebuild is small because it is mostly consolidation. The mode HUD layer (four independent implementations of the same three widgets, four palettes, three top offsets that collide, two of four still carrying the known per-frame-innerHTML FPS bug) cannot reach "coherent" by patching, because the defect IS that there are four of them. One `ui/routeAdvisor.js` (~260 lines) deletes ~400 lines across four files and is strictly less code than what it replaces. That is a rebuild that pays for itself in the same commit.

Four things get DELETED outright: compassBar.js (174 lines — it draws heading a second time, off-theme, and squats on the exact screen band the mode HUDs need; ETS2 has no such element and the minimap already carries heading), directionDisplay.js (58 lines, zero importers), style.css + public/fonts/*.otf (never loaded, and the Futura PT files are commercial Monotype on a public domain — a licence exposure, not just dead weight), and the world-space car-colour panel (carModel.js:506-600, which only exists to be re-parented into the ESC menu and hidden with four `!important` overrides at escMenu.js:37-43).

The progression system gets BUILT, because it does not exist. There is no design to refactor: 30 lines of wallet, one sink worth €1,400, one mode that pays nothing at all, no XP, no levels, no unlocks, no map. The user asked for a progression map by name; this is the only part of my domain that is net-new work, and it is deliberately designed to need ZERO re-bake and near-zero new art.

Finally, the single highest-leverage item in this domain is not UI at all: converting six menu PNGs to WebP hands 8.8 MB — 37% of the entire city-wide art download budget — back to the domains that actually need it, for half a day of work and zero risk. If nothing else in this plan lands, that should.
## ETS2 reference
ETS2's UI is one coherent system, not a set of widgets. Concretely: (1) LAYOUT — the screen centre is永 reserved for driving. Nothing transient sits above the horizon. All persistent UI is confined to the bottom strip (speed/gear/damage/fuel readout, ~8% of screen height) and ONE top-right "Route Advisor" box that the player cycles through pages (navigation map w/ route line, next-instruction arrow + distance, job info + delivery clock, cargo damage, radio). That single-consolidated-panel idea is the element we are missing entirely and the cheapest big win available. (2) PALETTE — near-black translucent panel (~rgba(20,18,16,0.75)), one amber accent (~#e8a022), white/warm-grey text, 1px hairline borders, zero gradients, zero bevels, zero particle celebration. It is deliberately plain. (3) TEXTURES — HUD art is a small set of .dds/.tobj atlases (icon sheet ≈512-1024px, single alpha channel for glyphs/icons), drawn in effectively one batch; total HUD texture footprint is a couple of MiB, not tens. Icons are flat single-colour silhouettes, no photo art. (4) TYPE — one condensed grotesque, ~11-13px caps labels with wide tracking for units, tabular numerals for speed/distance/money. Two weights total. (5) NAVIGATION — no giant world-space floating arrow, no 90m light pillars over objectives. Route is a line on the minimap + a text instruction + (optionally) a thin projected line on the road surface. (6) MENUS — the world map/garage/skills screens are flat dark UI with photographic panel art used sparingly, at modest resolution, and heavily compressed. (7) PROGRESSION — dual currency: € and XP. XP per job scaled by distance × cargo difficulty; levels grant skill points spent across 5 trees (Long Distance, High Value, Fragile, JIT, Eco, ADR), each tree gating access to better-paying job classes. € ladder: Quick Job (drive someone else's truck, fixed fee, no risk) → bank loan → own truck → Freight Market (you now pay fuel/tolls/ferry/damage) → buy a garage in a city → expand it 3→5 slots → hire AI drivers who generate passive income while you drive. Map regions are DLC-gated, not progression-gated; the in-game "progression map" is a world map with visited cities marked and a discovery percentage. CALIBRATION NOTE: against this bar our HUD is MORE decorated and LESS coherent. The ETS2 target here is a REDUCTION in decoration (kill the confetti, the emoji, the 44px/800 timers, the 90m light pillars) and an INCREASE in system coherence (one panel, one palette, one typeface, one update path). That makes this domain unusually cheap relative to every other v3 domain — we get closer to the bar by deleting.

VRAM 6 MiB of 200 (3%): HUD surfaces are compositor backing stores, not WebGL textures, but they occupy GPU memory all the same. Minimap 436x436x4 = 0.73 MiB resident (plus a transient 1080x1080x4 = 4.45 MiB while the expanded map is open — that is the 6 MiB peak). Speedometer 436x436x4 = 0.73 MiB. Route advisor + street display + ESC fab + day/night pill together under 0.4 MiB. Deleting compassBar RETURNS 0.64 MiB (1200x140x4). HUD icons ship as inline SVG, not a raster atlas, so they cost zero texture memory — this is why the ask is 6 and not the 10-12 an icon-sheet approach would need. DOWNLOAD 1.2 MB of 24 (5%), and this is a NET RETURN of 8.8 MB: today menu imagery alone is 10,446,044 B = 9.96 MiB (five 941x1672 PNGs at 7.53 MiB + logo 0.90 MiB + an orphaned title-bg.png 1.53 MiB), which is 41.5% of the whole city-wide art budget spent on six pictures. Rebuilt as correctly-sized WebP that becomes ~1.0 MiB; add ~0.06 MiB self-hosted Inter (two latin-subset weights, replacing ~0.10 MiB of render-blocking Google Fonts), ~0.02 MiB of inline SVG icons and authored JSON (landmarks + districts), ~0.12 MiB social card. The world-art domains should be handed the 8.8 MB difference. GPU 0.6 ms of 15.0 (4%): composited fixed layers cost roughly 0.05 ms each and the consolidated design holds the count to about twelve (down from the ~25 that exist today across four modes' scattered widgets); the in-world markers add at most 0.2 ms. Note separately that the minimap's vector redraw was measured at up to 10.1 ms of CPU on the ui thread and is throttled to one redraw per 180 ms (minimap.js:391-394), which amortises to ~0.94 ms/frame at 60 fps — that is CPU, not part of this GPU ask, and the P2 repalette does not change it. DRAWS 12 of 450 (2.7%): worst case is a Heat pursuit, 3 cop groups x (body + 2 light boxes) = 9, plus 3 spare. Dash peaks at 8 (two visible gates x 4 meshes, dashMode.js:243). Taxi and Rush Hour are 3. TRIANGLES 20,000 of 2.6 M (0.8%): dominated entirely by the three police.glb bodies at roughly 5k each; dash gates are 3,792 total and the taxi/delivery marker is 548. CRITICAL CAVEAT IN OUR FAVOUR: the stated p95 benchmark is 80 km/h at night in dense Eixample, which is free-roam driving. No game mode is running in that scenario, so this domain's actual contribution to the measured p95 is 0 draws and 0 triangles. The 12/20,000 is a worst-case reservation for a mode the benchmark never exercises, and it should be treated as such when the budget is reconciled.

## Risks
- LOAD-BEARING: the entire progression economy depends on the vehicles domain confirming that the existing city-car GLBs (loadCityCarTemplates, already used for cop cars at policeMode.js:48) are drivable-quality — collider fit, wheel anchor positions, scale. If they are not, the only money sinks left are eight paint colours worth EUR 1,400 total (carModel.js:520-527) and a EUR 3,000 garage, which is roughly 90 minutes of play before the currency becomes meaningless. There is no cheap substitute sink that does not require new art from another domain. This must be answered before P3 starts, not when P4 begins.
- Level-gating removes content that existing players already have. index.html:291-316 offers all five modes from minute one today; anyone with a dd_wallet or dd_*Best key who reloads into the new build and finds Heat locked will read it as a bug. The grandfather clause (seed XP from lifetime earnings on first run of the new build) is mandatory, not optional, and must land in the same commit as the gating.
- The routeAdvisor consolidation touches all four game-mode files simultaneously and deletes ~400 lines across them. It is the single highest-regression item in this plan. Mitigation is sequencing, not testing: land the panel wired to dashMode ONLY, verify, then port exactly one mode per commit. Do not do all four at once.
- The landmark list (34 POIs) and the district polygons are CONTENT AUTHORING, not code. They have no technical risk and a high slip risk, because nobody's day job is writing them. They are deliberately hand-authored rather than derived from OSM tags precisely so they cannot block on a re-bake — but that also means they cannot be generated and will simply not exist unless someone sits down and writes them.
- Mobile safe areas: the route advisor sits top-right, which on a notched iPhone in landscape is where the system puts the status cluster. touchControls.js already handles env(safe-area-inset-*) for the bottom clusters and speedDisplay.js:35-40 / minimap.js:20-26 already branch on (pointer: coarse) — the advisor must do the same or it will be clipped on exactly the devices the brief says we must scale down to.
- Deleting compassBar and the minimap compass ring in the same phase removes BOTH heading indicators at once if the sequencing slips. The minimap's fixed forward-pointing marker plus a north pip must be verified on screen before compassBar.js is deleted, not after.
- The car shop rebuild (P3 garage.js) deletes carModel.js:506-600, which currently owns the colour-selection side effects as well as the UI (selectColor, the sel class, the localStorage dd_carColor write at carModel.js:501). Extracting the UI without extracting the side effects will silently break paint persistence. carModel must retain setCarColor() and nothing else.
- Two of the four modes still carry the per-frame-innerHTML FPS bug that was already diagnosed and fixed in the other two (policeMode.js:87 called from :230, deliveryMode.js:111 called from :263). This is shipped code, not a design risk — but it means any performance measurement taken while Heat or Rush Hour is running is currently invalid, and any before/after comparison for this domain must state which mode was active.
- The mode-select art fetches 7.53 MiB at the moment PLAY is clicked (the images are behind display:none until index.html:498 adds .show, so they are not preloaded). Fixing the format without also preloading at PLAY-hover leaves a smaller version of the same first-impression stall on mobile.
- Futura PT OTFs sitting in frontend/public/fonts on a deployed custom domain are commercial Monotype faces. They are not loaded (style.css is never imported) but they ARE served — anyone can fetch them. This is a licence exposure under the free-assets constraint and should be deleted in P0 regardless of whether anything else in this plan is approved.

## Depends on
- VEHICLES — hard blocker for the economy. Must confirm whether the existing city-car GLBs are drivable (collider fit, wheel anchors, scale) before P3 progression design is committed. If no, the money sink collapses and the progression spine needs a redesign, not a patch. Also owns wheel/rim swaps (deferred to P4).
- ART DIRECTION / COHESION JUDGE — needs the P1 theme.js palette extension (gold #c9a227 + alert #c0553d + MODE_ACCENT map) locked before world-art work starts, so HUD accents, in-world objective markers and environment art are one system rather than three. This is a two-way dependency: I need their sign-off on the two new tokens, they need my token file to exist.
- AUDIO — should own a single UI sting API. Four near-identical Web Audio ding() implementations currently live inside the game-mode files (dashMode.js:252-262, taxiMode.js:270-276, deliveryMode.js:136-146, policeMode.js:100-107), plus a whole looping siren synth at policeMode.js:110-125. None of that belongs in a HUD/mode file. Also needed: a level-up sting and a landmark-discovery sting for the progression system.
- WORLD / POI DATA — soft dependency only, deliberately. The 34-landmark list could in principle be derived from tourism/historic tags already in the baked tiles, but I am designing it as hand-authored JSON specifically so this domain does NOT block on a re-bake. If world/POI later wants to supply a generated list, it is a drop-in replacement.
- TERRAIN / ROADS — the L15 'hill routes' unlock (dash routes that only spawn on graded roads) needs the road segment data to expose a grade or elevation-delta field. If it does not, that unlock degrades gracefully to a district filter instead. Non-blocking.
- PERFORMANCE / BUDGET RECONCILIATION — must be told that this domain's 12 draws / 20,000 triangles are reserved for a Heat pursuit, and that in the stated p95 benchmark (80 km/h at night in free-roam Eixample) no mode is running, so the domain's real contribution to the measured number is zero. Reconciling my worst case against their p95 as if both applied simultaneously would over-charge this domain by its entire ask.
- BUILD / DEPLOY — the P0 WebP conversion changes six asset filenames referenced from index.html and escMenu.js:16, and the Cloudflare Pages deploy must stop uploading frontend/public/fonts/*.otf and title-bg.png.
